# Uploader

Syncs new LMU and iRacing sessions to the lap app by itself, and reports its status to the app's Settings screen. Plan and contract: pit wall thread 30.

- `watch.mjs`: the loop. Every 30 s it checks the game processes and each sim's telemetry folder (LMU's Telemetry, iRacing's `Documents\iRacing	elemetry`), and runs `tools/sessions/sync.mjs --sim <id>` in a child process for each sim with something new. Each sim has its own sync state (LMU's is the top level of `state.json`, the others are under `sims`) and its own sync work folder; how a sim is treated is the `watcher` export of its adapter (`tools/sessions/lmu.mjs`, `iracing.mjs`). `LAP_SIMS=lmu` limits it to one sim.
- `trigger.mjs`: when to sync. Never while any watched sim runs (VR frame time beats upload latency). After the game exits, or at logon if telemetry is newer than the last sync (a PC crash mid-session needs nothing special). A session that fails waits on its own backoff (`retries.mjs`: 30 min, doubling, up to 8 h) and is skipped (`sync.mjs --skip`) until then; the other sessions and a version resync go ahead. Only a sync that crashes with no session blamed waits as a whole.
- `retries.mjs`: the per-session backoff map kept in `state.json`. The heartbeat state is `retrying` (with `retryAt`) while one is pending, `error` only after a crash: the heartbeat's `problems[]` then holds a `sync-crashed` entry (`sync crashed: <first error line>` with the time; a sync that exits before its closing `done` line).
- `heartbeat.mjs`: the `uploaders/{hostId}` doc. `problemsOf` builds its `problems[]` (at most 10, newest first, 120 characters, user folders, tokens and addresses removed): `sync-crashed`, one `session-failed` per backed-off session (its first `failed:` line, kept in `retries`), `recorder-layout`. The tray adds `uploader-stopped` itself (`trayFailure.mjs`, run by `sidecar.rs` when the uploader exits: reason, restart count, the last line of `uploader/sidecar.log`, and its own version as the doc's `version`). The server adds `not-seen` for a PC silent over 3 days. Settings > Problems lists them. The endpoint is public, so the id is a hash of the machine name, the name shown is `label` from `config.json` (`{"label": "Race PC"}`), and errors are one line with user folders scrubbed. (`GET /api/lmu/uploaders`, docs/API.md), written on each change and at least every 5 minutes. It copies the recorder's `%LOCALAPPDATA%\lap-capture\status.json` (tools/capture) into `recorder`; older than 2 minutes reads as `not-running`.
- `install.ps1`: registers the `LapUploader` logon task (headless, one instance, restarted on failure), running from the runtime clone (`tools/runtime`). Run it once; after later merges, `tools/runtime/update.ps1` is enough.

Local files, in `%LOCALAPPDATA%\lap-uploader\`: `watch.log` (every sync's output; rotated at 5 MB), `state.json` (last sync, per-session retries), `config.json` (optional). One instance holds the named pipe `\\.\pipe\lap-uploader-watch`; Windows frees it when the process ends.

Needs what `sync.mjs` needs: `npm ci --prefix functions` and `gcloud auth application-default login`.

Before a rollout, `node tools/sessions/sync.mjs --check` runs every step before the first write over all sessions (fingerprints, staleness, fold plan) and exits 1 on any throw; it analyses and writes nothing (about 2 min on the full set).

Test without touching the store: `node tools/uploader/watch.mjs --once -- --local --work <dir>` (everything after `--` goes to `sync.mjs`; `LMU_TELEMETRY=<dir>` points it at another folder).

End-to-end test of the watcher: `node --test tools/uploader/watch.e2e.test.mjs` (Windows only; skipped elsewhere). It runs the real `watch.mjs --once` against a fixture telemetry folder and a stand-in sync, through the seams `LAP_SYNC_SCRIPT`, `LAP_HEARTBEAT_FILE` (heartbeat docs to a file, not Firestore), `LAP_LOCK_PIPE` and `LAP_GAME_EXE`, and checks: new file, sync, heartbeat; a crash, `sync crashed`, the wait; the retry, and the error clearing.
