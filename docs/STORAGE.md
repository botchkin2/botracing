# Lap storage

How recorded sessions are kept. The decision and its reasons are in the pit-wall room (`decisions/2026-09-27-lasting-storage.md`).

## Where things live

| What                                                         | Where                                                                                                | Why there                                                                                               |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Recordings, sessions, laps (the numbers you filter and sort) | Firestore                                                                                            | Queryable, small docs, scales to many sims and users                                                    |
| Chart trace for one lap                                      | `gs://botracing-61-lmu/traces/{ownerId}/{lapId}/v2.csv.gz`                                           | Fetched only for laps being overlaid                                                                    |
| Full recording archive                                       | `gs://botracing-61-lmu/archive/{sim}/{sessionId}/{recordingId}/samples.parquet` and `events.parquet` | Our own sim-neutral copy of every channel, so analysis can be recomputed later                          |
| Consistency band                                             | `gs://botracing-61-lmu/bands/{ownerId}/{sessionId}/v1.json.gz`                                       | Median and p10/p90 of speed, throttle, brake on a 5 m grid                                              |
| Corner slices (every lap around each corner) | `gs://botracing-61-lmu/slices/{ownerId}/{sessionId}/{hash}/c{n}.json.gz` | The Corner screen draws every lap without fetching whole-lap CSVs. One small file per corner; the folder is named by content, so a resync never serves a stale slice |
| Measured track surface | `gs://botracing-61-lmu/surface/{trackId}/v1.json.gz` | The centre path and the road edges the game measured, summed per 10 m over every session's laps at a track layout, so a session adds to the old ones. One file per track, about 12 KB gzipped. The track doc's `surface` points at it |
| Field (every car, 5 Hz)                                      | `gs://botracing-61-lmu/field/{ownerId}/{sessionId}/{hash}.json.gz`                                   | From the local live capture (`tools/capture`), joined at sync time. No names. About 2 MB per race-hour. |

The raw `.duckdb` from LMU is never uploaded.

Nothing is deleted on a schedule.

## The archive

`samples.parquet` has one row per 100 Hz tick and one column per channel. Slower channels hold their last value. Values are fixed-point decimals by unit (0.01 km/h, 0.1 mm, 0.1 °C), which keeps a race-hour near 16 MB. Core channels have neutral names (`speed_kmh`, `throttle_pct`, `lap_dist_m`, ...). Every other channel keeps a slug of the sim's name, so nothing is dropped.

`events.parquet` is `(t, name, v1..v4)`, one row per change: `lap`, `lap_time`, `in_pits`, `gear`, `surface`, `impact`, and the rest.

A new sim needs one adapter that writes these two files. Analysis only reads them.

## Uploading

```bash
node tools/sessions/sync.mjs
```

It scans the LMU telemetry folder, skips files written in the last 3 minutes, groups recordings into sessions, and uploads only sessions that changed since the last run. `--local` writes everything to the work folder instead. `--list` shows the grouping. `--since YYYY-MM-DD` limits by day. It needs `npm ci --prefix functions` once and `gcloud auth application-default login`.

A session is recordings with the same sim, track layout, car, and session type, where the game's session timer kept pace with the wall clock between files (runs back to the pits) or restarted with the same session clock (a race restart).

## Online events

A recording does not say which online event it was. LMU's trace logs (`UserData\Log\trace_*.txt`) do: one line per server join, with the series name and the official event id. `tools/sessions/lmuEvents.mjs` reads them. A join lasts until the game returns to the main menu, the next join, or the end of that log. A recording that starts inside a join gets `event: {eventId, series, kind, joinedAt, gapS}` (`kind` is `practice` or `race`; the race server holds qualifying and the race). The session gets `series` and `eventId` from its first matched recording. Offline sessions get `null`.

LMU keeps only a few weeks of trace logs, so every join seen is kept in `events.json` in the work folder. Sessions older than the oldest log stay `null`.

`--events-only --since YYYY-MM-DD` sets these fields on sessions already uploaded, without analysis or archive uploads. Use it instead of a full resync to backfill.

## Access

The app never touches Firestore or the bucket. It calls the `lmuApi` function, which reads with the Admin SDK. The PC uploader writes with Google Cloud application-default credentials. `firestore.rules` denies all clients. The bucket is not linked to Firebase Storage and stays private through IAM.

There is no sign-in. Every doc carries `ownerId` and `sim` so that more than one driver and more than one sim fit later without a migration.

## Collections

- `recordings/{recordingId}`: one source file. Fields include `sessionId` and `startedAt`. One race can span several LMU files.
- `sessions/{sessionId}`: recordings grouped by owner, sim, track, layout, car, session type, and game session time. It holds the precomputed lap table, stints (each with `greenLaps` and the median and spread of fuel per green lap, `medianFuelL`/`fuelSpreadL`, and of Virtual Energy, `medianVePct`/`veSpreadPct`, null under 3 green laps: a green lap is timed, whole, not the first, no pit in or out, no full-course yellow, not cut short by a reset (LMU ends a recording at a reset; iRacing keeps one .ibt, so the uploader cuts the lap where the car lands in its pit stall straight from the track, `iracing.mjs` `resetTimes`, timed from the refill a tick before; that lap is partial and `endedInReset`, the next `afterReset`, and its fuel ends on the tick before the refill)), `fuel` (`startL`; `litresPerVePct`, the litres of fuel per 1 % of Virtual Energy measured as the median over green laps of used litres per used %, which depends on the fill limit and is not in the setup, and `litresPerVePctStop`, the same from litres and % added at the stops, a cross-check; `fillLimitL`, the most fuel the event lets the car take, from the car setup's `VM_FUEL_LEVEL` × 100, and `tankL`, `VM_FUEL_LEVEL.maxValue`, both null when the setup is empty), `race`, how long a race is, from the recorder's scoring stream (`tools/sessions/raceLength.mjs`): `{minutes}` (the minutes from the first green update to `mEndET`; every race is timed), null for other sessions and for a race with no capture (captures are pruned), pit in and out, the session consistency band, and `consistency`: every stint of the session (a stint with no selected laps reads `laps: 0` and `emptyReason`), each with its start reason, first and last lap, lap ids, pace trend and its 95% interval (`trendPerLapLow`/`High`, Sen's rank interval, null below 5 laps; it assumes independent laps, with outliers already out of the selection) and spread around the trend; scatter, off-pace laps, per-corner spread and loss, an `overview` text, and the thresholds used. Fields include `ownerId`, `sim`, `trackId`, `carId`, and `startedAt`.
- `laps/{lapId}`: one lap. It holds comparability reasons, a pointer to its trace, and everything `src/analysis/consistency.ts` needs to rerun on any selection of laps: stint lap, start, tyre carcass temperature, full-course yellow time, and per-section facts in `corners` (the lap cut at the layout's corner windows, see `tracks` and `trackBoundaries` below: `segTime` is the window's time, boundary to the next boundary, with `fromM` and `toM` in the map's frame; `runInS`, `cornerS` and `exitS` split it at the lap's own onset `onsetM` (where it began braking, or lifting for a section nobody brakes for) and where it reaches full throttle and holds it (95 % for 0.3 s, else 85 % for 0.5 s), and add up to `segTime`; `onsetSpeedKmh`, `fullThrottleSpeedKmh` and `endSpeedKmh` are the speed at those points and at the window's end; `brakeApps` lists the brake applications in the window, each `{onsetM, peakPct, part}` with `part` the corner it brakes for (null for a single corner); `pit` is true when the lap's pit lane overlaps this window, so only this window is not comparable; off-track and local-yellow time; minimum speed and where (`minSpeedAtM`, and `minSpeedPart`: the part it falls in), from the slowest recorded 100 Hz sample between turn-in and exit; brake point, full-throttle point; the two points are recorded pedal samples, with `brakeAtResM` and `fullThrottleAtResM` giving the distance since the previous sample, see `tools/sessions/pedalPoints.mjs`), each with `parts`: the same facts for every single corner inside the section, summing to the section's time. `startStraight` is the stretch from the line to the first window, `{segTime, fromM, toM, offTrackSec, localYellowSec, pit}`, so `startStraight.segTime` plus the sections' `segTime` add up to `lapTime` (to 0.01 s, over every lap of the Daytona archive); `cornerBoundaries` is `{v, rev}`, the boundaries these times were cut at (`tools/sessions/cornerFacts.mjs`). `fuel` holds the lap's fuel and Virtual Energy (`startL`, `endL`, `usedL`, `addedL`, `veStartPct`, `veEndPct`, `veUsedPct`, `veAddedPct`, and `green`: whether the lap counts as a green lap (see the stint medians), `lapsLeftFuel`/`lapsLeftVe`: the end level over the stint's median use, null without a median): used is start minus end plus what was added in the pits, read over the lap's whole time window so consecutive laps tile with nothing unaccounted for; `pitStop` (on the lap the pit lane is entered, its first if there are two) holds `atEntry` (`fuelL`, `vePct`), `added` (`fuelL`, `vePct`; 0 for a drive-through or penalty), `inPitS`, `lapsLeftAtEntry` (`fuel`, `ve`) and `visit` (`tools/sessions/pitVisit.mjs`, block version `blockVersions.pitVisit`, kept in `v`): why the car was in the lane, `{v, kind, detail, did, stationaryS, evidence}`. `kind` is `service` (stood still and fuel, VE or tyres were added or changed), `repair` (the live capture's dent severity or detached count was lower at the exit than at the entry; a repair outranks a service), `penalty` (a race only; with `detail` `stop-go`: stood still 3 s or more with nothing added and no repair seen; or `drive-through`: never stood still, nothing added), `through` (outside a race: a run through the lane without stopping or adding anything), or `unknown` (the window never ends, no speed channel, a stop with nothing added and no capture to say whether it was a repair, or outside a race, or something added without standing still); `did` lists everything that happened (`refuel`, `tyres`, `repair`); `stationaryS` is the time under 1 km/h; `evidence` says why in words. The capture is pruned after a week, so an older session's idle stop reads `unknown`. The pit-loss and refuel-rate learners take `service` only. `tyres` (`changed`, `wheels`, and `entryPct` and `exitPct`: each wheel's wear at pit entry and a second after pit exit, so a new tyre reads exit above entry; `exitPct` is null when the session ended in the pits; `wheels`: the wheels among `FL FR RL RR` whose wear reading rose by more than 0.5 % within 0.25 s inside the pit window (0.5 sits between the channel's float noise, at most 0.011, and the smallest real change, 98.7 to 100; it was 5 %, which missed a tyre swapped after a short run), plus a second either side; a single wheel is a real case; null without a wear channel); `coolDown`: for each wheel that was not replaced, the change in rubber temperature, carcass temperature (C) and pressure (kPa), pit entry against 45 s (`afterS`) after pit exit, each the median of 5 s (the window ending at pit entry; the window centred on 45 s) with dead zeros left out; a replaced wheel, a dead sensor, a stop that never ends, or a window past the recording's end is null, and a cooling stop is not a tyre change; `compound`: `'start'` or `'other'` when all four wheels were replaced and the game's compound event right after the exit gives the same code on all four: 'start' if it equals the code in force at the start of the recording, else 'other' (the code is an index into the car's options, so it means nothing alone; no file names a compound, so none is guessed), otherwise null; a pit window in the first 30 s of a recording is the drive off the grid, not a stop; both are null without the channels (`tools/sessions/fuelFacts.mjs`, evidence in pit-wall thread 34). `tyres` (`tools/sessions/tyres.mjs`, `src/analysis/tyres.ts`, block version `blockVersions.tyres`, kept in `v`) holds, per wheel as `{FL, FR, RL, RR}`: `wearPct` at the end of the lap, the lap's median `pressureKpa`, `hotPressureKpa` (the stabilised hot pressure: the median pressure of the lap's last 5 s outside the pit lane, kept only from the third lap of a stint and null on the first two, where it has not settled; pressure follows the gas and carcass temperature, which change over tens of seconds, not the surface that cools on a straight, so an end-of-lap reading is fair here where one for temperature would not be), `rubberC` (the outer rubber layer), `carcassC` and `treadC` (the median temperature of the tread's `inner`, `centre` and `outer` thirds per wheel, from `TyresTempLeft/Centre/Right`, which are car-fixed: Left is the car's left edge on all four wheels, so the inner third is Right on the left wheels and Left on the right wheels, the outer edge being the cooler one with negative camber; a wheel or a third with no live reading is null), taken over the lap's ticks outside the pit lane with dead-sensor zeros left out (a reading at the line would be one 10 Hz sample from the main straight, where the tyres cool); a wheel with no channel or only dead readings is null, and a field is null when the recording has no such channel. `changed` lists the wheels with a new tyre in the pit stop that ended during this lap (the same per-stop test as `pitStop.tyres`, so a full set, one wheel or none; null without a wear channel); the lap after it is the first on new tyres, as is the lap after one that ended in a reset to the garage; consistency counts that as cold tyres, and `freshTyres` in `src/analysis/tyres.ts` is its one definition (the uploader and the app's `Lap.newTyres` both call it). `tyres` is null on a lap analysed before it existed or without any of the channels. The compound is not stored: no recording names it. `hybrid` (`tools/sessions/hybrid.mjs`, block version `blockVersions.hybrid`, kept in `v`) is the battery and motor energy of a Hypercar lap, from the `SoC` and `Regen Rate` channels; null on a car without a hybrid (an LMP2 or a GT3 logs both flat at 0) and on a lap analysed before it existed. `Regen Rate` is in **watts** although the file labels it kW: positive is regen into the battery, negative is the motor deploying (integrated as watts against the change in SoC it gives one constant, about 0.013 kWh per 1 % SoC, a usable battery of about 1.3 kWh; as kW it would be 1000 times too big; pit-wall/ideas/2026-09-30-hypercar-hybrid-audit.md). It holds `socStartPct` and `socEndPct` (read at the ends of the lap's whole time window, as the fuel is, so consecutive laps tile), `deployKwh` and `regenKwh` (the integral of the power over that window, the pit lane included: a lap with `pitlane` overlaps one) and `netKwh` (regen minus deploy, from the rounded two), `peakDeployKw` and `peakRegenKw`, `sections` (per corner window of the layout, the start straight as `section: null`, `{section, fromM, toM, deployKwh, regenKwh, netKwh, socStartPct, socEndPct}`, `netKwh` being regen minus deploy; the windows are the lap's corner windows, so they tile the lap's distance; null where the lap has no corner windows) and `liftCoast`: every lift before a braking zone, `{atM, brakeAtM, fromKmh, toKmh, coastS, coastM}`, found as the driver's unfiltered throttle under 5 % and no brake (under 10 %) for at least 0.5 s above 80 km/h (the floor sits above the 0.04 to 0.16 s pedal change of an ordinary braking zone, from the one Hypercar file), ending where a brake application starts, with `count`, `seconds` and `metres` totals; a facts-only measure, it does not say which deploy or regen mode the driver chose (the file has the setup strings only). A stint's entry in the session's `stints` carries `hybrid`: `socStartPct`, `socEndPct`, the SoC trend `socPerLapPct` (least-squares slope over the green laps' end-of-lap readings against the lap's number in the stint, null under 3 green laps), `greenLaps`, and the stint's `deployKwh` and `regenKwh`. `traffic` holds the cars around the player from the field, in seconds and counts (`draftS`: within 30 m behind a car in the same lane above 200 km/h; `trafficAheadS` and `trafficBehindS`: a car within 1 s on the road in the same lane; `blueFlagS`: seconds with a car of a faster class within 1.5 s behind on the road, derived from the field for every car, because the game's own flag latches on the player while a lap down, `gameBlueS` being that flag as recorded; `passesMade` and `passesSuffered`: passes on the road with cars of the player's class, including a slower car of the same class being lapped, so not a place change (a Hypercar lapping a GT3 is not counted); `draftSpans`: where the tow was, the same `{fromM, toM, s}` objects as `aheadSpans` with `draftS`'s rule, so their seconds add up to `draftS`; `aheadSpans` and `blueSpans`: where on the lap, `{fromM, toM, s}` objects, one per run of consecutive updates (objects, not arrays: Firestore refuses an array inside an array), 0.1 m resolution, with the rule of `trafficAheadS` and `blueFlagS` so each one's seconds add up to the lap's; `passMarks`: `{atM, made}` per own-class pass; `fieldLapM`: the field's lap length, the frame of those distances (the app scales them by the map length over it, as the corner slices do); `passesMadeAll` and `passesSufferedAll`: every car; `battleS`: seconds within 1 s of a car of the player's class, ahead or behind, in any lane, including a lapped one), null when the session has no field; see `tools/sessions/fieldTags.mjs` for the evidence behind each threshold. The block also carries `v` (`TRAFFIC_VERSION`, `src/analysis/traffic.ts`) and `overtakes`: the cars of a faster class (hypercar over LMP2 over GT3/GTE, `paceClass`) that went from behind the player to ahead of them during the lap, each `{cls, atM}` with `atM` the player's lap distance (not the overtaking car's), in lap-distance order (a pass is the on-road gap changing sign inside 150 m; cars in the pits, and the player's own or a slower class, are left out). A sync without the capture (pruned after 7 days) reads the uploaded field instead of writing `traffic: null`. `excluded` says why the lap is not in the default "normal racing" selection; `consistency` holds its residual to the pace trend and where it lost time. Fields include `ownerId`, `sim`, `sessionId`, `lapNumber`, `trackId`, `carId`, and `lapTime`.
- `trackBoundaries/{trackId}`: what the layout's corner boundaries rest on (`tools/sessions/layoutBoundaries.mjs`): per session and section, the number of its comparable green laps (no pit, yellow or off-track), how many braked for it, their median speed at the section's entry, and two 5 m histograms of where they began braking and where they began lifting, kept by session id so a resync replaces its own laps and never counts them twice; the kind of onset per section (brake where most pooled laps brake for it, else lift, decided again at every fold; a flip moves the windows and bumps the rev), the earliest onset each start rests on (null until the pool holds 20 laps from 2 sessions, when the map's entry stands in), the starts, margins, `rev`, the rule version `v` and `mapKey` (boundaries kept for another map are replaced). Written by the uploader when a session changes it; sessions cut at an older `rev` are re-analysed by the next sync. Packed (only non-empty bins), because Firestore takes no array inside an array.
- `tracks/{trackId}`: one track layout's corner map (`src/analysis/corners.ts`), so corner numbers stay the same from session to session. Custom sectors and official turn names will attach here. It is made by the curator, not by a sync: `node tools/curate/curate.mjs plan-add <trackId> --session <id>` (a dry run first; `--apply --reason` writes it, with history in `trackHistory`; see `tools/curate/README.md`). Syncs that upload (remote or Admin) read it and never create or replace one; only `sync.mjs --local` still builds maps, and uploads nothing. The map is made from a session with at least 8 clean laps of the same length. A session the stored map does not fit (lap length off by more than 3%) is analyzed with a map of its own, which is not stored, and the session doc says so (`trackMapSource`, `trackMapMismatch`). Replace a map on purpose with `curate.mjs plan-replace`. A map with an older `mapVersion` counts as no map and is rebuilt the same way; version 3 groups corners into sections by how the driver links them (a braked corner with a straight before it starts a section; lifts and flat corners join their neighbours); version 4 puts a corner's apex at its slowest point, or at its tightest point when the slowest is on the turn-in or exit edge (a corner taken while accelerating, or flat). Anything the driver sets on a track (edited sectors, turn names) goes in its own field, never inside the generated map, and refers to corners by `apexM`, so a rebuild or a new `mapVersion` never discards it. The uploader also keeps a copy in its work folder (`tracks/{trackId}.json`). `boundaries` is the layout's corner windows (`src/analysis/cornerBoundaries.ts`): `{v, rev, startsM, marginM, windows}`, where `startsM` and `marginM` are per section, and `windows` tile the lap from the line to the line (`{kind: 'start-straight' | 'section', section, fromM, toM, parts: [{n, turnInM, fromM, toM}]}`, parts only for a compound section), all in the map's frame (lap fraction times the map's length). A section's window starts 0.5 s (at the median speed there) before the 5th percentile of where laps at the layout begin braking for it, never behind the previous section's exit, and ends where the next one starts; the start/finish line is always a boundary. `rev` goes up only when a start would move by more than its margin, so a few metres of drift do not re-cut every session.

The same analysis code runs in the uploader and in the app, so a selection made on the phone gives the same numbers the uploader stored for the default selection. `node tools/sessions/consistency-report.mjs --work <dir>` checks that on `--local` output.

IDs are deterministic hashes, so re-uploading the same file overwrites instead of duplicating.

Firestore docs cap at 1 MiB. Anything per-sample goes in the bucket.

## Indexes

`firestore.indexes.json` covers these queries:

- An owner's sessions, newest first, optionally at one track.
- A session's recordings in order.
- A session's laps in order.
- The best laps for an owner at a track in a car.

Rules and indexes deploy with functions on merge to main (`firebase deploy --only functions,firestore`).

## Corner slices

`tools/sessions/cornerSlices.mjs` cuts, for every lap and every corner of the track map (parts count as corners), the window apex-350 m to apex+200 m, widened to the corner's own window (its part's, or its section's) plus 50 m each side when that reaches further, out of the lap's trace and writes one file per corner: `slices/{ownerId}/{sessionId}/{hash}/c{n}.json.gz`. The session doc has `slices: {format, hash, prefix, corners, beforeM, afterM, stepM}`. The hash is over the files' content; a sync writes the new folder, then deletes the session's other slice folders after the doc points at the new one. Format and route: `docs/API.md`.

What a slice holds is what the app draws from the lap's CSV today, produced by the same code (`src/analysis/traceCsv.ts` and `resample.ts`, run by the uploader): every channel's **recorded samples** at their own distances (slower channels are not held or repeated), plus time, latitude and longitude on the 5 m grid. Format 2 adds gear, a step channel (each grid point holds the last recorded gear, and the samples are the recorded gears at their distances). Format 1 files have no gear and still read, with an empty gear channel; a sync rewrites them as format 2.

**Format 2 in full.** A slice file is `{v: 2, corner, apexM, lengthM, stepM, digits, windowM, laps}`, with `v` the file's `SLICE_FORMAT` (`tools/sessions/cornerSlices.mjs`). Each lap carries `id`, `gridFromM`, `timeS`, `lat`, `lon` on the 5 m grid, and `samples` for the channels `speedKph`, `throttlePct`, `brakePct`, `steeringPct`, `pathLateralM`, `trackEdgeM` and `gear`, each `{d, v}` (distances and values, both integer deltas over the file's `digits`). The decoder (`src/analysis/cornerSlices.ts`) accepts `v` 1 and 2. A format 1 file has no `gear` samples and reads them as empty; a format 2 file without `gear` is an error. Gear is decoded as recorded integers (0 digits) and rebuilt on the grid by holding the last recorded value (`steppedFromSamples`), never interpolated: a downshift shows as a step at the distance it was recorded.

**Rollout.** The format is listed in `blockVersions` as `cornerSlices` (`tools/sessions/analyze.mjs`), so the session fingerprint changes with it and the watcher re-syncs every stored session once on its own; nobody has to resync by hand. Until a session is re-synced it still holds its format 1 slices and shows an empty gear trace. The app reads whichever format the session doc names. Values keep the CSV's own precision, distances are millimetres, and every array is integer deltas. Measured on the Road Atlanta 44-lap race (11 corners): 104 to 180 KB gzipped per corner, 1.6 MB for the whole race, against about 0.55 MB per lap when the app fetched the CSVs.

Each file's `windowM` is the window it holds. The widening is capped at 300 m past the screen's own window (`EXIT_REACH_M`), because a corner whose window runs a long way to the next boundary (Daytona's last corner, to the line past the tri-oval) would hold two kilometres at 100 Hz, 181 KB gzipped for 14 laps against 62 KB. Capped, that file is 850 m (about 95 KB for 14 laps, 54 B per metre as the others); the time, split and speeds of a corner are the lap's own corner facts, not read from the slice. Every other Daytona file is unchanged.

Limits: the window is clipped at the start/finish line (a corner within 350 m of the line has a shorter window, as the per-lap CSV path always did); the file lists every lap the session has, including pit and partial laps; a trace from before analysis version 9 has no lateral samples.

## Field

When the recorder (`tools/capture`) was running, `sync.mjs` joins its captures to the session (`tools/sessions/field.mjs`). A capture joins when its time window overlaps the session's and its track matches (the scoring name, or the recording's venue or layout). It is then aligned on the session clock: field `et` and the `.duckdb` GPS Time are the same clock. The alignment is checked: the player car's lap distance must agree between the two sources to within 20 m (median). If it doesn't (a restart or rejoin reset the clock), the session gets `field: null` and the sync logs why.

A capture the recorder never closed (no `endUtc`: crash, kill, power) ends at its last chunk, so it cannot join a later session on the same track. Cars are labelled with the model the recorder read from each car's telemetry slot (`meta.vehicleModels`), never the entry name, which carries the car number.

The session doc then has `field: {path, hash, hz, cars, durationS, captures, alignM}`. The file name is a hash of its content; a new field replaces the file (deleted after the doc points at the new one). A sync that finds no field (captures pruned, the capture folder not visible, a failed clock check) keeps the stored one. `captures` lists the capture folder names; the uploader's pruner treats a capture listed there as uploaded. Each car's heading (`yawCrad`, file version 2) comes from the game's orientation matrix; older files (`v: 1`) lack it. An existing field is rewritten on the next `analysisVersion` change while its capture is still local (7 days). The file carries no driver names or car numbers, because the API is public and the session's `eventId` would name every car in one lookup. The names stay in the local capture. An iRacing car also carries `classId` (the sim's class id) and `classLabel` (`tools/sessions/irClasses.mjs`: a known id by its class, GTP, LMP2, LMP3, GTE, GT3, GT4; else the sim's short name; else the one model, or `<most common model> +N` for a class that mixes models). They come from the capture's car list when the tray wrote class ids, else from the .ibt's DriverInfo by car index; a stored iRacing field without them, whose capture is gone, is rewritten with them matched by model (`relabelField`, during any sync of the session). LMU cars name their class in `class` and carry neither. The session doc also carries `traffic: {v, clean, traffic}` (`src/analysis/traffic.ts`): over the comparable laps, `{laps, medianS}` for the clean laps (under 2 s within 1 s behind a car, not passed by any car of any class, no blue flag, under 2 s of battle with a car of the player's own class, and no faster-class overtake) and the traffic laps (5 s or more); a lap with 2 to 5 s is in neither, on purpose, so the two never become one threshold; `medianS` is null under 3 laps. It is deliberately not a "traffic costs X seconds" number: on the two full Daytona fields (534 laps) running within 1 s behind a car shows no lap-time cost (median 0.0 s), and the clean laps are the front-runners. Null without a field. The session doc also carries `classLaps` (analysis version 17, `src/analysis/classLaps.ts`, run by `sync.mjs`): `{version, kind, classes, startGapsS}` for the Plan's class timing. `classes` is, per pace class (`hypercar`, `lmp2`, `gt3`, `gte`, `other`; GTE is not pooled with GT3), `{cars, laps, medianS, p10S, p90S}` over every car's green laps, or null when no class reached 3 laps (and always for qualifying, where everyone is on a single-lap push). `kind` (`race`, `practice`, `qualify`) is stored with the numbers; a practice keeps a car's laps only within 1.07 times that car's own best. A lap is the time between two crossings of the line (a lap-distance wrap that lands at zero or more, with a physical step: at a race start the counter drops by a lap to about -450 m, 450 m before the line, which is continuous on the road and is not a crossing; a jump bigger than one update of driving is not one either), interpolated from the speed just after the line; it counts when the car was in the field, out of the pits and under no flag for all of it, and lies between 0.95 and 1.15 times the class median (the floor is applied before any car's best is taken). `version` is `CLASS_LAPS_VERSION`: a sync without the capture keeps the stored doc while its version and kind are current, and otherwise works it out from the uploaded field file, so a rule change needs only a version bump (version 2 added `startGapsS`). `startGapsS` (races only, else null) is, per class other than the player's, `{firstS, lastS}`: the seconds from that class's first car (the leader, the biggest head start) and from its last car first crossing the line to the player's first crossing (negative for a class that gridded behind); the class arrives as a train, so the Plan's first catch is a band between the two; a car that first crosses more than 60 s after the field's first is a pit-lane start and not counted, and it is null when no flagged player crosses in that window. Null without a field. The session doc also carries `result` (`src/analysis/raceResult.ts`, run by `sync.mjs`): `{version, kind, finish}`, where `finish` (races only, else null) is `{overall, inClass, ofOverall, ofClass, lapsDone, leaderLapsDone, classLeaderLapsDone, leftEarly}`, the player's place at their last line crossing (the laps counter's last step up; the last update would read last, since a car back in the garage is scored behind everyone): the game's overall place, the place among the cars of the player's class, the cars in the field and in the class then, the player's laps at that crossing, the most laps any car had by the end of the field (`leaderLapsDone`), the most laps any car of the player's class had then (`classLeaderLapsDone`, version 3: the race's length for the player's car, since a faster class runs more laps in the same minutes; the Plan reads this one), and `leftEarly`, true when the leader crossed the line after the player's last crossing. The field has no chequered-flag column, so that is how an unfinished race is told. `version` is `FINISH_VERSION`: a sync without the capture keeps the stored doc while its version and kind are current, and otherwise works it out from the uploaded field, so a rule change needs only a version bump. Null without a field.

## Track surface

`tools/sessions/surface.mjs` folds every session's lap traces (comparable, not partial, no pit lane) into one file per track layout: per 10 m bin along the lap, sums of the centre path (position minus `PathLateral`) and of the left and right asphalt edge (`TrackEdge`), plus the laps behind each, in the game's own metres before any georef. The file lists the sessions already folded in, so a re-run or a resync adds nothing twice; a session whose traces predate analysis version 9 (no `PathLateral`/`TrackEdge`) is left out until its traces are re-uploaded. It reads what is uploaded, so it needs no analysisVersion bump and no resync. `sync.mjs` runs it by itself after each sync for the tracks it just uploaded (a failure there is one log line, `surface: not updated: ...`, and does not fail the sync); by hand, run `node tools/sessions/surface.mjs` after a sync (`--dry` to see what it would add, `--track <trackId>`, or `--api <base> --out <dir>` to build read-only from the public API). If the track map's length changes, or the file was built under older rules (`SURFACE_RULES` in surface.mjs, stored as `rules`), the file is rebuilt from every session. Rules 2 leave out lap 0: a race's grid lap reads LapDistPct 0 for a minute and pulled Sebring's first bin 80 m off the road. `node tools/sessions/surfaceAudit.mjs` lists, per track, what OSM the app still draws next to the measured road and any jump in the measured path, and writes an SVG of each. The rules, and the measurements behind them (centres of different recordings agree to 0.3 m, edges are seen only on the car's side, so most bins have one edge for a long while), are in `src/analysis/trackSurface.ts`. Route: `docs/API.md`.

## Uploading without Admin credentials

`tools/sessions/store.mjs` holds the upload logic (what to skip, what to keep from the stored session, what to delete afterwards) over a small backend: documents and files. `adminBackend` is the PC uploader above. `storeClient.mjs` is the same backend over HTTP, for a machine that signs in as a user: `sync.mjs --remote` (or `LAP_API`) with `LAP_TOKEN_FILE` pointing at a file that holds the user's Firebase ID token. The wire format is in the header of `storeClient.mjs`. The owner key comes from the server (`GET /me`), not from `--owner`: a new user's is their uid, Botkin's stays `botkin` so existing ids and paths remain valid. The server sets that mapping by an admin script only, never from a client endpoint.
